# 비판적 검토 보고서 — adaptive-orchestrator v0.3.0

- 검토일: 2026-07-16
- 방법: 전체 소스 정독 + 7개 차원(내구 저장, 실행/검증, 라우팅/학습, CLI/설치, 통합 정합성, 보안, 테스트 품질) 병렬 리뷰 + 발견별 코드 대조 판정 + 실증 재현(재현 가능한 결함은 전부 실행으로 확인)
- 기준선: 141개 테스트 중 1개 실패 → 검토 후: 158개 테스트 전부 통과

## 총평

설계 문서와 README가 주장하는 통제 경계(얇은 게이트, claim/attestation 분리, fail-closed 신뢰 정책, 복구 가능한 파일 상태)는 대체로 코드에 실재하며, 테스트가 그 의도를 상당히 밀도 있게 고정하고 있다. 그러나 **주장과 구현 사이의 틈**이 여러 곳에서 실제 결함으로 확인됐다. 특히 (1) 한국어 게이트 패턴 전체가 사문이었던 점, (2) `--dry-run true`가 실제 실행되는 점, (3) 복구 도구가 유효 데이터를 삭제하는 점, (4) 거짓 partial claim이 무검증 통과하는 점은 이 프로젝트가 내세우는 안전 서사와 정면으로 충돌하는 결함이었다. 모두 수정했다.

## 수정된 주요 결함 (심각도순)

### 안전 경계 위반

1. **한국어 분류 패턴 사문화** — JS 정규식 `\b`는 `[A-Za-z0-9_]` 기준이라 한글 옆에서 매치되지 않는다. 한국어로 문서화된 프로젝트에서 한국어 프롬프트가 전부 기본값(read-only/fail-open)으로 분류되고 있었다. 테스트에 한국어 케이스가 하나도 없어 잡히지 않았다.
2. **파괴적 명령의 read-only 오분류** — `drop the users table in production`(개발 동사 없음), `... and show me what remains`(표시 동사 포함), `deploy ..., do not modify any files`(명시적 읽기전용 표현으로 외부 액션 은폐)가 모두 low/fail-open으로 분류됐다. 파괴 동사 거부권과 명시적 읽기전용의 한계를 규칙에 반영했다.
3. **`--dry-run true` → 실제 실행** — 불리언 플래그가 뒤따르는 값을 삼켜 문자열 `'true' !== true`가 되면서, 안전을 위해 존재하는 플래그가 정확히 반대로 동작했다. 오타 플래그 무시, NaN 타임아웃(타임아웃 해제로 강등)도 함께 수정.
4. **거짓 partial claim 무검증** — 변경 대조는 `complete` receipt에서만 실행되어, worker가 `partial`로 보고하면 in-place 체크아웃의 실제 변경을 숨길 수 있었다. 비완료 receipt에도 claim-대-실제 diff 대조를 강제.
5. **ID 충돌 신뢰 승격** — 설정 템플릿과 이름이 겹치는 홈 디렉터리(`~/.claude/skills`) 산출물이 템플릿의 `trusted` 등급을 상속받아 critical 작업에 선택될 수 있었다. user-scope 발견은 보수적 병합으로 변경. 암묵적 `reviewed` 기본값 주입도 제거.

### 데이터 유실

6. **`doctor --repair`의 중간 손상 처리** — sequence 검증이 연쇄 실패를 일으켜, 중간 한 줄 손상 시 이후의 유효한(체크섬 정상) 레코드 전부가 이슈로 분류되고 repair가 이를 영구 삭제했다. 이제 손상이 유효 레코드에 선행하면 자동 복구를 거부하고 수동 개입을 요구한다.
7. **torn-tail 이어붙음** — 개행 없이 찢어진 마지막 줄 뒤에 append하면 새 레코드가 조각에 이어붙어 함께 오염됐다(양쪽 구현 모두). 훅 측 journal은 sequence도 원시 줄 수로 세어 복구 후 모든 후속 기록이 무효화됐다.
8. **직렬화 전 체크섬** — 페이로드를 메모리 객체 기준으로 해시하고 디스크에서 파싱된 값으로 검증하므로, `Date` 등 toJSON 값이 있으면 기록 즉시 영구 판독 불가가 됐다.
9. **잠금 회수 TOCTOU** — 두 프로세스가 동시에 스테일 잠금을 발견하면 한쪽 unlink가 다른 쪽의 방금 만든 잠금을 삭제해 상호배제가 깨졌다. rename 기반 원자 회수 + 내용 검증으로 교체(6-way 경합 스트레스 테스트로 확인). PID 재사용/EPERM으로 영구 회수 불가가 되는 경로에는 하드 연령 상한 추가.

### 신뢰성/정합성

10. **stdin EPIPE 크래시** — worker가 stdin을 읽지 않고 종료하면 미처리 스트림 오류로 오케스트레이터 전체가 죽었다(10MB 프롬프트 + 즉시 종료로 실증).
11. **worker 무한 행** — 기본 타임아웃 0으로 워치독이 아예 비무장 상태였다. 60분 기본값 도입(명시적 0으로 해제).
12. **라우터의 `provider.enabled` 무시** — 비활성 provider의 모델이 선택된 뒤 실행 단계에서야 실패했다.
13. **`localeCompare` 동점 처리** — 호스트 로케일에 따라 동일 입력에서 다른 라우팅이 나올 수 있었다. 코드포인트 비교로 교체.
14. **lesson confidence 복리 인플레** — 저장된(보너스 포함) 값에 다시 보너스를 더해 2차 증가했고, 같은 회고를 재저장할 때마다 +0.02씩 올랐다. 원시 증거 confidence를 별도 보관해 멱등 계산으로 변경.
15. **심볼릭 링크 별칭 오판** — active-run 포인터 격리 검사가 realpath를 해석하지 않아, 별칭 경로로 만든 run이 "state root 밖"으로 오판되고 `--repair`가 살아 있는 포인터를 삭제할 수 있었다.
16. **Stop 게이트 조용한 무력화** — 포인터가 가리키는 run 파일이 없으면 "활성 run 없음"으로 처리되어 회고 강제가 사라졌다. 손상 상태로 구분해 차단하도록 수정.
17. **모노레포 훅 실패** — codex 훅이 `git rev-parse --show-toplevel` 기준이라 하위 패키지 설치 시 매 프롬프트 실패했다. 상향 탐색으로 교체(중첩 디렉터리 기능 테스트 추가).
18. **로그인 셸 증거 오염** — 검증 명령을 `/bin/sh -lc`로 실행해 사용자 프로필 출력이 SHA-256 해시되는 증거 로그에 섞였다(기준선의 테스트 실패 원인이기도 함). 비로그인 `-c`로 교체.
19. **빈 run 100% 완료 보고** — task 0개인 run이 `complete/100%/high confidence`로 보고됐다. planning/0%로 수정.
20. 기타: `task.write` 불리언 미검증(문자열 `'yes'`가 읽기전용으로 강등), 빈 `complexities` 배열이 "모든 복잡도 허용"으로 해석, `estimateRouteQuality`의 `now` 미검증(NaN 전파), task patch로 `id`/`weight` 덮어쓰기 가능, `--limit 0`이 10으로 해석, 검증 명령 0개 + 변경 증거 없음이 `pass` attestation으로 세탁(→ `inconclusive` 신설, executeTask도 이를 low confidence로 강등), 예제 관측치가 카탈로그상 생성 불가능한 조합, 설치 대상에 스키마 미복사, 설치 병합 전 기존 JSON 사전 검증 부재.
21. **오도성 진단 메시지** — critical 라우팅에서 후보가 0개일 때도 "No proven route"(challenger 문제로 오도), untrusted capability의 write 차단이 "not allowed for low risk"로 보고, doctor의 provider 실패 사유가 빈 문자열(`'' ?? fallback` 미도달). 각각 원인별 메시지로 분리.
22. **dead export 겸 footgun** — `saveRun`은 어디서도 사용되지 않으면서 lock 아래에서 재독 없이 caller 스냅샷을 덮어써 동시 갱신을 유실시키는 API였다. 제거하고 mutateRun 경로만 남김.
23. **격리 검사 4중 복제 중 1곳 비일치** — cli의 run 참조 격리 검사만 realpath를 해석하지 않아 심볼릭 링크 루트에서 나머지 3곳과 다르게 동작했다. 정렬 완료.

## 테스트 스위트 평가

기존 141개 테스트는 의도(불변식) 서술이 명확하고 행동 기반이라는 점에서 상질이나, 다음 축이 비어 있었고 이번에 보강했다(+31개, 총 172개): 한국어 게이트 분류 전체, 파괴 동사/명시적 읽기전용 상호작용, 잠금 하드 스테일·live-owner 비회수, 중간 손상 복구 거부, toJSON 페이로드 왕복, torn-tail append, state-root 탈출 포인터 거부, task patch 화이트리스트/터미널 가드, 라우터의 제약 전면 배제·정책측 우선순위 가드·비활성 provider, 불리언/미지/숫자 플래그 CLI 거부, 기존 사용자 훅 보존·손상 설정 사전 거부·루트 지침 파일 불가침, 모노레포 하위 디렉터리 훅 동작, 매달린 포인터의 Stop 차단, inconclusive attestation과 confidence 강등, evidenceDigest 내용 결합 검증, 검증 명령 타임아웃 실패, untracked 파일 워크트리 재현, 거짓 partial claim 거부. 남은 커버리지 공백: claude/codex receipt 파싱 어댑터(현재 generic 어댑터만 테스트 경유), 실제 provider CLI 계약 테스트.

## 수정하지 않은 알려진 한계 (기록)

- **gitignore된 파일은 변경 증거 밖** — 변경 대조는 `git status` 기반이라 `.gitignore`에 걸리는 파일(.env 등)의 변경은 보이지 않는다. README가 이미 "훅은 OS 샌드박스가 아니다"라고 명시하듯, 변경 증거는 격리·권한·네트워크 정책과 함께 쓰는 신호이지 봉쇄 수단이 아니다. `--ignored` 수집은 node_modules 규모에서 검증 비용을 감당할 수 없어 채택하지 않았다.
- **`verificationCommands`는 임의 셸 실행** — task JSON은 신뢰 입력이라는 것이 설계 전제다. task 작성 주체(오케스트레이터 LLM)가 오염되면 이 경계는 무의미하므로, 위험 작업은 provider 권한/워크트리/네트워크 정책과 병행해야 한다.
- **저널 무한 성장 + append마다 전체 재파싱** — O(N²) 총비용. 관측치가 수천 건 규모가 되면 회전/컴팩션이 필요하다. 시간 감쇠 모델과 결이 맞는 개선 후보.
- **`saveRun`의 blind write** — 내부에서 사용되지 않는 export이지만, load→modify→save 패턴 소비자는 경합 시 갱신 유실을 겪을 수 있다. mutateRun 스타일로의 이전 권장.
- **수동 `aorch verify`는 write claim을 attestation할 수 없음** — before/after 스냅샷은 exec 흐름만 캡처한다. fail-closed가 맞는 동작이므로 오류 메시지와 README에 한계를 명시하는 것으로 정리했다.
- **원시 카탈로그의 미선언 provider는 trusted로 간주** — 라우터 직접 호출(API) 시의 관용 정책으로 테스트가 의도를 고정하고 있다. CLI 경로는 validateConfig가 미선언 provider를 원천 거부하므로 도달 불가.
