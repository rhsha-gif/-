# Adaptive Orchestrator v0.6.0: Adaptive Lanes and Provider-Aware Prompt Compiler

## Status

Approved by the user's explicit request to implement v0.6.0 from the preceding design discussion.

## Goal

Make the orchestrator use the user's selected host model intelligently, avoid unnecessary model calls for low-risk work, compile delegated tasks into provider/model-appropriate prompts based on versioned official guidance, and expose shadow-routing and actual model-use evidence without adding an always-on service or autonomous self-modification.

## Design principles

1. **The user's selected model is the host, not automatically every worker.** The host interprets the request and may execute directly, delegate, or escalate according to `preferred`, `pinned`, or `bootstrap-only` policy.
2. **Decompose only when decomposition improves independent correctness.** Low-risk simple work stays in one delivery unit. Deterministic verification remains mandatory even when LLM reviewers are skipped.
3. **Prompting is compilation, not free-form rewriting.** A canonical task envelope is transformed by a versioned provider/model prompt profile and checked by a deterministic linter before dispatch.
4. **Official guidance is snapshotted, not fetched on every task.** Prompt profiles record official source URLs, verification dates, model families, and revisions. Updating a profile remains a proposal-and-benchmark control-plane change.
5. **Shadow routing is observational.** It records a viable alternative route and optionally requests a read-only shadow review. It must not double-execute ordinary changes by default.
6. **Actual model use is visible.** The system distinguishes host, router, executor, reviewer, verifier, and shadow roles in a trace.
7. **No new operational platform.** Keep dependency-free Node.js ESM, JSON/JSONL state, existing thin hooks, and proposal-only harness changes.

## Current baseline and prerequisite defect

The imported v0.4.0 baseline has 170 passing assertions, but `test/verifier.test.js` does not terminate. The timeout test launches a command through `/bin/sh`; `runCommand()` kills only the shell process, leaving the Node grandchild holding inherited stdout/stderr pipes. v0.6.0 must first add process-tree termination and output bounds so the baseline suite becomes reliably finite.

## Architecture

```text
User prompt
  ↓
Thin gate
  ↓
Host context + host policy
  ↓
Lane classifier
  ├─ Direct: host executes one bundled delivery unit
  ├─ Bundled: at most one specialist worker by default
  └─ Orchestrated: explicit task graph and independent review
  ↓
Task signature + route selection
  ↓
Prompt profile selection
  ↓
Provider-aware prompt compiler
  ↓
Prompt linter + prompt manifest
  ↓
Bounded worker
  ↓
Independent verifier
  ↓
Trace + optional shadow observation
  ↓
Post-run reflection
```

## 1. Host context and selection policy

### Host context

A host context is explicit data, not an inferred global singleton:

```json
{
  "provider": "anthropic",
  "requestedModel": "sonnet",
  "resolvedModel": "claude-sonnet-5",
  "requestedEffort": "high",
  "effectiveEffort": "high",
  "selectionMode": "preferred",
  "source": "explicit"
}
```

Supported `source` values are `explicit`, `environment`, `config`, and `unknown`. The CLI accepts a host JSON file and individual host flags. Environment detection is conservative: only documented variables are read. Unknown model identity is allowed, but direct execution is limited to routes whose capability requirements can still be established.

### Host selection modes

- `preferred`: use the host directly when eligible; other models may be delegated when materially better or required by policy.
- `pinned`: provider/model delegation is disallowed except deterministic verifier processes. If the host cannot satisfy the task, return a blocked route instead of silently switching.
- `bootstrap-only`: the host performs the thin classification and invokes a dedicated router/worker for standard-or-higher tasks. Low-risk simple tasks may still execute directly when policy explicitly permits it.

The host model's success is measured separately from worker success. Trace roles are `host`, `router`, `executor`, `reviewer`, `verifier`, and `shadow`.

## 2. Execution lanes

### Direct lane

Use when all are true:

- risk is `low`;
- ambiguity is low;
- one coherent deliverable;
- limited repository/edit breadth;
- no public contract, schema, auth, finance, concurrency, destructive, or external side-effect change;
- deterministic verification is known;
- the host is eligible under the current selection mode.

Budget:

```json
{
  "maxTasks": 1,
  "maxExternalModelCalls": 0,
  "maxLlmReviewers": 0
}
```

The host receives a short execution contract and performs inspect → edit → focused test → diff review in one context.

### Bundled lane

Use for low-risk work that benefits from one specialist or has modest breadth. The default budget is two task records but one external worker call. Exploration, implementation, focused tests, and diff inspection stay in the same worker bundle unless a reviewer could meaningfully accept one part and reject another.

```json
{
  "maxTasks": 2,
  "maxExternalModelCalls": 1,
  "maxLlmReviewers": 0
}
```

### Orchestrated lane

Use for standard-or-higher risk, high ambiguity, multi-system changes, unclear failures, state/concurrency work, external side effects, security, auth, finance, migrations, or escalation after repeated failures.

The existing global `maxTasksPerRun` remains a hard ceiling. Lane budgets are lower defaults, not targets.

### Escalation

A lane may only escalate, never silently downgrade, after evidence appears:

- actual scope exceeds the declared signature;
- host or worker reports an undeclared architecture decision;
- verification fails twice with the same failure class;
- a critical risk signal is discovered;
- routing confidence is below the configured threshold.

Escalation creates a trace event with the old lane, new lane, evidence, and reason.

## 3. Task signature

The canonical task gains a compact signature:

```json
{
  "ambiguity": "low",
  "repositoryBreadth": "local",
  "editBreadth": "few-files",
  "contextVolume": "small",
  "toolIntensity": "medium",
  "stateComplexity": "none",
  "testCoverage": "good",
  "externalIntegration": "none",
  "language": "javascript",
  "framework": "node"
}
```

Enums keep the feature deterministic and easy to validate. The signature informs lane and route eligibility; it does not replace risk or complexity.

## 4. Prompt profiles

Prompt profiles live under `prompt-profiles/` and are included in the npm package. Each profile contains:

- stable ID and schema version;
- provider, model family, applicable roles, task kinds, and lanes;
- official source URLs and `verifiedAt` date;
- composition rules;
- required and forbidden sections;
- output contract preference;
- model-specific guidance;
- profile revision and status (`stable`, `challenger`, `retired`).

Initial profiles:

1. `anthropic-claude-general-2026-07`
   - clear/direct instructions;
   - explain relevant motivation;
   - XML sections for complex prompts;
   - inspect referenced code before claiming facts;
   - explicit tool-action intent;
   - avoid overengineering and test-specific hacks;
   - parallel tool calls only when independent.
2. `openai-codex-sol-2026-07`
   - precise objective, constraints, invariants, failure policy, and strict output schema;
   - optimized for complex professional/coding work.
3. `openai-codex-terra-2026-07`
   - bounded repository context, coherent implementation bundle, verification and scope policy;
   - optimized for balanced everyday work.
4. `openai-codex-luna-2026-07`
   - one objective, short rules, narrow scope, deterministic verification, minimal alternatives;
   - optimized for cost-sensitive high-volume work.

Official references are metadata and documentation inputs. Profiles do not fetch the internet at runtime.

## 5. Provider-aware prompt compiler

### Canonical input

The compiler consumes:

```text
validated task
+ route
+ lane decision
+ host context
+ selected capability IDs
+ relevant context summaries
+ output schema path
+ prompt profile
```

### Claude output

Claude prompts use consistent XML sections when the task is delegated:

```xml
<role>...</role>
<objective>...</objective>
<context>...</context>
<scope>...</scope>
<requirements>...</requirements>
<acceptance_criteria>...</acceptance_criteria>
<tools>...</tools>
<verification>...</verification>
<failure_policy>...</failure_policy>
<output_contract>...</output_contract>
```

Direct-lane Claude execution uses a short `<execution_contract>` rather than generating a second full worker prompt.

### OpenAI/Codex output

Codex prompts use explicit, compact headings:

```text
ROLE
OBJECTIVE
WHY
REPOSITORY CONTEXT
ALLOWED SCOPE
FORBIDDEN SCOPE
REQUIREMENTS
SUCCESS CRITERIA
VERIFICATION
FAILURE POLICY
OUTPUT CONTRACT
```

Luna omits nonessential prose and accepts only one objective. Terra keeps a coherent implementation bundle. Sol includes invariants and failure cases when available.

### Prompt manifest

Every delegated prompt creates a manifest containing:

```text
prompt ID
run/task ID
host context
lane
provider/model/revision/effort/role
prompt profile ID/revision/source metadata
selected capabilities
context identifiers, not raw secrets
prompt SHA-256
output schema ID
lint result
created timestamp
```

The prompt text is stored with evidence redaction. Hidden verifier commands are never included.

## 6. Prompt linter

The deterministic linter rejects prompts that:

- omit objective, scope, acceptance criteria, failure policy, verification, or output contract when required;
- expose hidden verifier commands;
- request control-plane changes without an approved proposal;
- tell a read-only worker to edit;
- lack allowed scope for a write task;
- ask Luna to handle multiple independent objectives;
- delegate from a direct lane;
- include capabilities not present in the selected exact-ID set;
- exceed configured prompt bytes;
- copy an unbounded parent transcript;
- contain unresolved placeholders.

Warnings cover duplicated instructions and excessive context. A warning does not block dispatch unless configured as strict.

## 7. Shadow routing (P2)

Shadow routing chooses one eligible alternative after the primary route is fixed. By default it does **not** execute the task again.

A shadow record contains:

```json
{
  "selectedProfileId": "claude-sonnet-general",
  "shadowProfileId": "codex-terra-general",
  "reason": "similar conservative quality; insufficient task-signature samples",
  "mode": "record-only"
}
```

Supported modes:

- `off`;
- `record-only` (default for eligible standard work);
- `review-sample` (read-only review on a configured percentage of accepted changes).

A shadow route must differ by provider or model family, meet risk/trust requirements, and stay within a separate per-run shadow budget. It never performs a second write implementation automatically.

## 8. Actual model-use trace (P2)

The runtime writes append-only trace events for:

- host registration;
- lane classification;
- route selection;
- prompt compilation;
- worker start/finish;
- verifier start/finish;
- reviewer or shadow execution;
- escalation;
- final integration.

`aorch trace --run active` returns both JSON and a concise human-readable view:

```text
Host: Claude Sonnet 5 / high (preferred)
Lane: bundled
Executor: GPT-5.6 Terra / high
Prompt profile: openai-codex-terra-2026-07
Verifier: deterministic / git-worktree
Shadow: GPT-5.6 Luna / medium (record-only, not executed)
Escalations: none
```

The trace distinguishes requested and effective model/effort when known. Unknown effective values are printed as unknown rather than guessed.

## 9. CLI changes

Add commands:

```text
aorch lane --task <task.json> [host flags]
aorch prompt compile --task <task.json> [host flags] [--output dir]
aorch prompt lint --manifest <manifest.json>
aorch trace --run <id|active> [--json]
```

Extend `route` and `exec` with:

```text
--host-file
--host-provider
--host-model
--host-resolved-model
--host-effort
--host-effective-effort
--host-mode preferred|pinned|bootstrap-only
--shadow off|record-only|review-sample
```

`exec` compiles and lints the prompt before provider command construction. Existing direct callers remain compatible when no host data is supplied; they use configured host defaults and bundled/orchestrated worker routing.

## 10. Integration behavior

The installed Claude and Codex `adaptive-orchestrate` skills are updated to:

- classify direct/bundled/orchestrated lane before task decomposition;
- keep low-risk simple work in one task;
- avoid external calls in direct lane;
- pass explicit host context when the CLI can reliably determine it, otherwise mark it unknown;
- invoke `aorch prompt compile` before delegated worker execution;
- report actual host/worker/reviewer/shadow use at completion.

The thin `UserPromptSubmit` hook remains a deterministic classifier and does not load prompt profiles or run route scoring.

## 11. Error handling

- Missing prompt profile: fail closed for delegated execution and list compatible profiles.
- Stale profile: warn after configured age; block only if explicitly configured.
- Prompt lint failure: do not call provider; persist lint diagnostics.
- Pinned host ineligible: return blocked route with reason.
- Direct lane scope expansion: stop and escalate; do not silently continue.
- Shadow failure: record separately; it does not invalidate the accepted primary result unless the shadow reports a configured critical finding.
- Unknown effective host configuration: allow noncritical routing but lower confidence and expose uncertainty.

## 12. Testing strategy

- Unit tests for host validation, lane classification, task signature, prompt profile matching, prompt compilation, linter rules, shadow selection, and trace formatting.
- Golden prompt fixtures for Claude, Luna, Terra, and Sol.
- Regression test for process-tree timeout so the complete suite exits.
- Integration tests for `route → prompt compile → provider command` and direct-lane no-call behavior.
- Install smoke tests confirming prompt profiles and updated skills are packaged.
- Full suite repeated three times to detect process leaks.
- Clean ZIP and npm tarball replay.

## 13. Non-goals

- Runtime web synchronization of official documentation.
- Automatic prompt-profile modification.
- Automatic model discovery via undocumented endpoints.
- A second scheduler inside workers.
- Duplicate write implementations for shadow comparison.
- A database, daemon, dashboard, or distributed queue.
- Replacing deterministic verification with an LLM judge.

## 14. Success criteria

1. Low-risk simple tasks classify to direct lane and generate no delegated worker prompt.
2. Low-risk broader tasks default to one coherent bundled worker prompt.
3. Delegated prompts are compiled from versioned official-source profiles and pass deterministic lint.
4. Luna, Terra, Sol, and Claude profiles produce materially different prompt structures appropriate to their intended roles.
5. Pinned host policy blocks silent provider/model switching.
6. Shadow routing records alternatives without duplicate write execution.
7. `aorch trace` clearly reports host, lane, executor, prompt profile, verifier, reviewer, shadow, and escalation history.
8. The complete test suite terminates and passes reliably.
9. v0.6.0 packages install cleanly and include prompt profiles, schemas, skills, and docs.

## Carry-forward runtime integrity invariants

The uploaded baseline predates several safety boundaries already agreed in the v0.5 design. v0.6 must carry them forward rather than ship a feature-rich but weaker runtime.

### Bounded execution and verification

Worker execution uses catalog budgets for timeout, process-tree kill grace, combined output bytes, and receipt bytes. Verification separately limits each command, the total verification window, combined output bytes, and total check count. Budget failures produce failed evidence instead of disappearing as wrapper errors.

### Explicit non-Git evidence

Tasks may declare exact project-relative `evidenceFiles`. These files are fingerprinted before and after execution and replayed into isolated verifier worktrees even when Git ignores them. Recursive ignored-tree scanning is forbidden.

### Secret-safe persistence

Worker and verifier outputs are parsed and verified in bounded memory, then redacted before persistence. Redaction metadata and hashes are retained, but raw secrets are not intentionally written to evidence artifacts. File-based receipts must be bounded regular non-symlink, non-hard-linked files.

### Tamper-evident journals

New journal records use a checksum chain by including the previous record checksum. Legacy records remain readable. Torn tails may be repaired; mid-journal chain corruption is reported and not destructively rewritten.

### Scoped one-time control-plane approval

A task that changes protected harness files must be critical, isolated, independently verified, and reference an approved proposal. Actual changed protected files must be a subset of the proposal's `affectedFiles`. Approval is consumed only after a passing attestation and cannot be reused.

## 9. Carry-forward integrity invariants

v0.6 does not weaken earlier control-plane boundaries while adding lower-call direct and bundled lanes.

- Worker and verifier process trees have explicit timeout and output budgets.
- Worker receipts remain claims; verifier attestations remain completion evidence.
- Git-ignored exact-path evidence participates in before/after comparison and isolated replay.
- Persisted evidence is best-effort redacted and raw values are represented by digests.
- JSONL journals retain sequence/checksum validation and link v2 records with `previousChecksum`.
- Control-plane changes require an approved immutable file scope, one task reservation, critical isolated execution, hidden verification, and one-time consumption after a passing attestation.
- A direct/bundled lane is never allowed to bypass those controls merely to save a model call.
