# Adaptive Orchestrator v0.6.1 Bootstrap-Only Hardening Design

## Goal

Correct v0.6.0 so every substantive project task is executed by a bounded worker invocation, while low-risk simple work remains one coherent worker task with no separate router model or LLM reviewer. Harden lane monotonicity, thin-gate classification, provider metadata, and official-source prompt-profile governance without adding a daemon, database, nested scheduler, or automatic self-modification.

## Critical review findings

### 1. Host-direct execution contradicts the required architecture

v0.6.0 still contains a `direct` lane, `host-direct` route, and `compileDirectExecutionContract()`. An eligible host can therefore edit product files in the same context that interprets the user request and integrates the result. This violates the agreed separation:

```text
host = bootstrap, decomposition, routing, integration
worker = bounded investigation, implementation, and focused tests
verifier = independent completion evidence
```

The replacement is a `single-worker` lane. It creates one bundled task, invokes one worker, uses no separate router model, no LLM reviewer, and no executing shadow worker.

### 2. Explicit lane values can downgrade safety

The current CLI and task runner accept `task.executionLane` directly. A high-risk task can request `bundled` or `direct`, bypassing the classifier's stronger lane. Explicit lane input must be monotonic: it may strengthen a decision but never weaken it.

### 3. The thin gate can misclassify external actions as read-only

An explicit negative file-edit clause currently demotes requests such as “deploy the migration but do not modify config” to a read-only request. File mutation and external side effects are different dimensions. An external action such as deploy, push, publish, database deletion, or trading execution must remain high-risk even when no local file edit is requested.

### 4. Raw router use trusts undeclared providers

`providerMetadata()` currently synthesizes a trusted/stable provider when catalog metadata is missing. This is fail-open behavior at the provider boundary. Models referencing an undeclared provider must be ineligible in both CLI and direct library use.

### 5. Prompt-profile provenance is official-domain-only, not provider-bound or freshness-bound

An OpenAI profile can currently cite an Anthropic official domain, and an old profile remains active indefinitely. Prompt profiles must:

- cite official domains belonging to the selected provider;
- remain within a configured verification age;
- reject future-dated verification records beyond a small skew;
- expose freshness diagnostics in the prompt manifest;
- continue to require model-family, role, and task-kind compatibility.

### 6. Luna prompts omit explicit acceptance criteria

The concise Luna profile includes verification commands but not a dedicated success-criteria section. Deterministic tests are not always equivalent to the user's outcome. Every delegated worker, including Luna, must receive concise acceptance criteria.

### 7. Model-use trace does not clearly prove bootstrap-only execution

The trace records host and executor but drops host selection mode in its summary and does not report external model-call count. The trace must make it explicit that the host did not execute the task and that the single-worker lane used exactly one worker call.

### 8. Record-only shadow is observational metadata, not performance evidence

A non-executed shadow cannot prove that another model would perform better. v0.6.1 will preserve record-only shadow because it adds no extra write call, but documentation and trace semantics must explicitly call it a counterfactual candidate, not comparative performance evidence. No model promotion may consume record-only shadow data.

## Architecture

```text
User prompt
  ↓
thin gate: classify request and external-action risk
  ↓
bootstrap-only host
  ↓
base lane classifier
  ↓
monotonic explicit-lane resolver
  ├─ single-worker: 1 task, 1 worker, 0 router-model calls, 0 LLM reviewers
  ├─ bundled: 1–2 tasks, normally 1 worker per task, 0 router-model calls
  └─ orchestrated: risk-dependent task graph and review
  ↓
risk-first deterministic route selection
  ↓
provider-bound, freshness-checked prompt profile
  ↓
provider-aware prompt compiler and deterministic lint
  ↓
bounded worker
  ↓
independent verifier
  ↓
host integration and trace
```

## Host semantics

`hostPolicy.executionMode` is fixed to `bootstrap-only`. The existing `selectionMode` remains a route preference:

- `preferred`: prefer an eligible separate worker matching the host provider/model inside the quality-equivalent tier;
- `pinned`: require the separate worker route to match the host provider/model;
- `bootstrap-only`: do not prefer the host route.

None of these modes permits product-file edits in the host context.

## Lane policy

### single-worker

Eligibility:

- risk `low`;
- complexity `low` or tightly bounded `standard`;
- no protected control-plane scope;
- no complex state or mutating external integration;
- low ambiguity and coherent acceptance criteria.

Budget:

```text
maxTasks = 1
maxExternalModelCalls = 1
maxLlmReviewers = 0
shadowExecution = false
```

The worker prompt bundles inspection, characterization, implementation, focused tests, and final diff review.

### bundled

Used for low-risk broader work or standard work that remains one or two coherent deliverables. It does not call a separate router model. Explicitly choosing `bundled` cannot downgrade an `orchestrated` base decision.

### orchestrated

Mandatory for high/critical risk, protected control-plane scope, high ambiguity, wide repository scope, complex state, mutating external integrations, repeated failures, and evidence-based escalation.

## Prompt profile governance

Prompt-profile validation uses provider-specific source allowlists:

```text
anthropic → platform.claude.com, code.claude.com
openai    → developers.openai.com, platform.openai.com, cookbook.openai.com
```

`promptCompilation.maxProfileAgeDays` defaults to 120 and `maxFutureSkewDays` defaults to 1. Compilation fails closed when no current compatible profile exists.

Prompt manifests include:

```text
promptProfileVerifiedAt
promptProfileAgeDays
promptProfileFresh
source publisher/document/url
```

All prompts continue to use structured output schemas. Luna receives a short `SUCCESS CRITERIA` section in addition to `VERIFY`.

## Error handling

- Missing provider metadata: no eligible route.
- Explicit weak lane: replaced by the stronger base lane with an escalation reason.
- Stale or cross-provider prompt profile: compilation failure before worker launch.
- High-risk external action with negative file-edit phrase: high-risk, durable run recommended, fail closed.
- Legacy `direct` task lane: rejected with a migration message.
- Legacy `lanePolicy.direct` config: accepted only as a migration alias and normalized to `single-worker`; new output never emits `direct`.

## Compatibility

This is a maintenance release with one intentional behavioral correction:

```text
direct / host-direct → single-worker / delegated
```

Existing configs with `lanePolicy.direct` are migrated in memory. Task envelopes that explicitly request `executionLane: direct` fail with a clear instruction to use `single-worker`.

## Tests

The release requires tests for:

- no host-direct code path;
- one delegated command in single-worker lane;
- lane downgrade prevention;
- external-action gate classification;
- undeclared provider rejection;
- provider-bound source domains;
- stale and future prompt-profile rejection;
- Luna success criteria;
- trace selection mode and external call count;
- record-only shadow not being represented as evidence.

Full `npm run check` must pass repeatedly, and the final ZIP and npm package must be replayed in clean temporary installations.
